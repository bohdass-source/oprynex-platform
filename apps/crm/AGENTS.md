Oprynex App — the CRM (and later the SaaS) behind https://site.oprynex.workers.dev.

- Hosting: Cloudflare Worker "app" → https://app.oprynex.workers.dev, deployed with `bun run cf:deploy`. No Worker secrets: the browser talks to Supabase with the publishable key and row level security does all access control.
- Database: the shared Supabase project your-project-ref (Frankfurt). The site repo (oprynex-site) owns migrations 0000–0099 (lead intake, chat quotas); this repo owns 0100+ in drizzle/migrations. Apply them with the Supabase MCP or SQL editor and keep the file identical to what was applied.
- Before deploying: `bun run test:node26`, `bunx tsc --noEmit`, `bun run build`.

Data model (database/migrations/0100_crm_core.sql):
- Every CRM row has a workspace_id; members see only their workspaces (RLS via private.is_workspace_member). Build every new table the same way, even while there is a single workspace, so the SaaS needs no rework.
- Leads arrive only through the website's service-role function accept_lead; the column default puts them into the Oprynex workspace (00000000-0000-4000-8000-000000000001). Members may read leads and update only status, assigned_to, product and value_eur (0101_deals.sql). Pipeline: new → contacted → proposal → won / lost, plus spam.
- products (0120_lead_products.sql) lists every product of a request (chatbot, website, crm, consulting, consulting_plan = the consulting package "Analyse & Plan", other); product is kept equal to its first entry by a trigger, older values erp, mvp and cloud count as other. Without an agreed value the estimate is the sum of the starting prices; value_eur is the agreed net value in whole euros. While they are empty the app guesses the product (chat topic, then page, then words in the message, src/lib/products.ts) and counts the published starting price as an estimate, always marked "≈". START_PRICE must stay equal to `prices` in oprynex-site/src/lib/offers.ts.
- Status changes are written to lead_events by a trigger; members log notes, calls and emails (kind note/call/email) and delete their own entries. Tasks may belong to a lead and must stay in that lead's workspace (private.lead_in_workspace).
- Import, merge and roles (0102_import_merge_roles.sql): leads with source 'import' are the owner's existing contacts, so they skip the site's consent and message-length rules (consent=false, consent_at empty); website leads keep those rules. Owners and admins import (RLS insert policy, source must be 'import', no future dates) and merge duplicates through public.merge_leads (history and tasks move to the kept request, the other's message becomes a note, the other is deleted). Roles: owner does everything, admin everything except changing roles, member works leads and tasks; src/lib/crm.ts `can()` mirrors the policies and the team page shows the matrix. A trigger keeps at least one owner. public.workspace_team lists members with their emails.
- Client websites (0103_client_sites.sql, grants in 0104): each site built from oprynex-site-template is a row in public.sites (workspace, name, url, SHA-256 of its intake token, daily limit). The site's Worker holds only the token (secret SITE_INTAKE_TOKEN) and calls public.accept_site_lead with the publishable key; the function checks the token, consent and email, limits 5 requests per visitor and site per hour plus the site's daily limit, and saves the lead with site_id into that workspace. Members see their sites but never the token hash. Supabase gives anon and authenticated full rights on every new public table by default, so each new table needs REVOKE ALL before its own grants (0104 does this for sites).
- Deleting requests (0106_delete_leads.sql): owners and admins delete a request from its page or all spam requests at once from the spam tab (DSGVO erasure, test clean-up); history and tasks go with it by cascade. Members cannot delete.
- Client chatbots (0105_client_bots.sql): each bot is a row in public.bots (workspace, optional site, enabled, name, business, allowed origins, languages de/en/ru, greeting, knowledge, quick replies, colour, privacy link, daily limits). One engine serves all bots: Worker "bot" (repo oprynex-bot, https://bot.oprynex.workers.dev) with only the publishable key plus its own token (secret BOT_ENGINE_TOKEN, SHA-256 in private.bot_engine_tokens). It calls only public.bot_engine_config, public.accept_bot_question (10 per visitor and minute, visitor_daily_limit, daily_limit, 5000 a day for the engine) and public.accept_bot_lead (consent, 5 per visitor and hour, 100 per bot and day; source 'bot_lead', bot_id and site_id set). Chat texts are never stored; public.bot_usage counts questions per bot and day for members. Owners and admins edit bots; members only read.
- Oprynex Cloud (0107_cloud_plans_signup.sql): workspaces have plan (internal, start, team, business), status (trial, active, paused) and trial_ends_at. Seats and the Start plan's missing admin role are enforced by triggers on invites and members (Start 2, Team 5, Business 12 users; CLOUD_PLANS in src/lib/crm.ts must equal `prices` in oprynex-site/src/lib/offers.ts). Self sign-up (public.create_workspace: one company per account, 14 day trial, caller becomes owner) works only while private.cloud_settings.signup_open is true; it stays closed until AGB, Datenschutz and AVV for Cloud exist. Oprynex admins (private.platform_admins, seeded with the Oprynex owner) see /admin: every workspace, plan, status, trial end, and the sign-up switch, through platform_* functions. public.accept_my_invites runs at every sign-in so invitations also reach existing accounts. A person in several workspaces switches in the sidebar (remembered per browser). No billing yet: Stripe comes later; trial end shows a banner but does not block work.
- Support tickets (0108_tickets.sql): public.tickets (number, subject, customer name and email, channel, status open/pending/solved/closed, priority urgent/high/normal/low, assignee who must be a workspace member, optional lead_id in the same workspace) and public.ticket_messages (internal notes, logged replies, status changes written by a trigger). Members read, create and change tickets and add or delete their own messages; owners and admins delete tickets. Replies are recorded, not sent: the member mails the customer from their own program (mailto with [#number] in the subject). A request page opens a ticket with its details; open tickets count in the bell and the live refresh also watches tickets.
- Assignment (0109_assignees.sql): a request's or ticket's assignee must be a member of its workspace (leads_update and tickets policies check private.user_in_workspace); when someone leaves a workspace a trigger clears their assignments there. The request page has an assignee picker with "take it", the requests table filters by assignee (owner=me|none|<user id> in the URL) and the bell lists open requests assigned to the signed-in member.
- Customer card (no migration): /customers groups requests and tickets of one person by lower-cased email in the browser (customersFrom in src/lib/crm.ts; spam left out; name and company from the newest contact; won value summed); /customers/<email> shows both lists. Request and ticket pages link to it.
- Integrations by plan (0110_integrations_by_plan.sql): website chatbots need a workspace on Business or internal that is not paused (private.workspace_has_integrations; bots_insert/bots_update policies; bot_engine_config returns null otherwise, so the engine stops serving the bot within a minute). Website forms (sites) stay independent of the plan. /integrations is the hub for website forms (read-only list with request counts), chatbots and CSV import; the menu shows it instead of separate Bots and Import entries. hasIntegrations in src/lib/crm.ts mirrors the rule.
- Push notifications (0111_push_notifications.sql): devices subscribe from the bell (service worker public/sw.js, manifest for installing the CRM as an app; iPhone needs "Add to Home Screen" first) and their endpoints are saved per user in public.push_subscriptions. A new request (not import or spam) or ticket makes private.notify_push call POST /api/push through pg_net with the endpoints of the workspace's members except the creator; the call carries a token kept only in private.push_hook, the Worker checks its SHA-256 (PUSH_HOOK_SHA256). The Worker sends empty VAPID-signed pushes (src/lib/push.server.ts), so no request content goes through Apple, Google or Mozilla; the service worker shows a fixed text. One-time setup: `bun scripts/setup-push.ts` stores the private key as Worker secret VAPID_PRIVATE_JWK and writes the public key into src/lib/push-key.ts (commit, deploy). While that key is empty the bell keeps the in-tab alerts.
- Access is by invitation: a row in workspace_invites (lower-case email) turns into a membership when that email first signs in (trigger on auth.users). A signed-in user without membership sees "No access".
- SECURITY DEFINER helpers live in the private schema, never in public, so they are not callable through /rest/v1/rpc.

App:
- Screens: dashboard (key figures with change against the previous period, stages, top products, languages, requests over time, latest requests, next tasks; every figure links to the requests behind it), pipeline board (drag and drop, plus a move menu on each card for keyboard and touch), requests table (filters in the URL, sort, inline status and product, saved views in this browser, rows rendered virtually), request page (deal card, history grouped by day, other requests from the same address with merge), tasks, import wizard (CSV file, column mapping guessed from the headers, check with errors and duplicates, batches of 200; src/lib/importer.ts), team (members, invitations, permission matrix). All figures are computed in the browser from the leads (src/lib/analytics.ts); spam never counts.
- Look: sidebar layout, dark by default like the owner's reference dashboard, light theme on request (remembered per browser, applied after hydration). Gold marks the active page and key figures.
- Sign-in is a Supabase magic link (PKCE). The Supabase Auth URL configuration must list https://app.oprynex.workers.dev/** (and http://localhost:8090/** for development) as redirect URLs.
- The session exists only in the browser, so the server renders the loading state and the gate in src/routes/__root.tsx decides between login, no access and the app. Data is read and written with React Query hooks in src/lib/queries.ts.
- UI texts live in src/lib/i18n.tsx in German, Russian and English; German is the default and a chosen language is remembered per browser. A test checks every text exists in all three.
- The app is private: robots noindex, no analytics.
